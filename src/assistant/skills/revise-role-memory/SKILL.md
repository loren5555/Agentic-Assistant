# Learn from a researcher's feedback

Read the current human comment in the context of the decision it responds to. The researcher writes ordinary feedback. Infer its scope from what they meant; special wording or an explicit request to remember is unnecessary. The proposal, external sources and generated results explain the situation. The human's own comments supply evidence about their working preferences.

Identify which future decision would improve. Organizer decides what supplied material merits archiving and what calls for follow-up. Proposer decides how to frame an outstanding task, its scope, proposed deliverable or clarification. A comment about factual accuracy, execution or a tool failure may concern neither role.

A clear continuing preference can justify a revision after one observation. For an inferred pattern, look for consistent reasons in independent earlier tasks. A single-task instruction applies to the current item. A bare review status leaves the reason unknown. When the evidence is ambiguous, preserve the notes; the observation remains available for a later review. Treat newer corrections as evidence about the scope of earlier preferences.

Read each affected notebook as a whole. Revise the paragraph that governs the decision. Merge related advice, preserve established preferences and their exceptions, and narrow or remove an inference the researcher has corrected. Use the researcher's language. Keep each notebook concise enough to read in full (up to 4,000 characters). Put provenance and the reason for this change in the review result; the notebook should contain usable guidance.

For example, a user may collect tutorials as references but also ask to reproduce a specific table with their own data. A preference for archiving reference material should support both the archive-only decision and the explicit reproduction task. Test your wording mentally against a similar case that should produce a different decision.

Return the complete new text only for roles that need a change. Use null for unchanged roles and an empty string when the last applicable preference is withdrawn. Summarize the evidence and expected effect briefly, including why a one-off comment requires no update. The application owns permissions, review requirements, available tools and role definitions; these stay in the project's manually maintained instructions.
